# Echo FSW — Flight 2 Changes

This document summarizes what was changed vs the state of the repo as
uploaded, what problems it addresses, and how to deploy the result on the
Pi.

---

## 1. Camera data-loss fix

### Symptom (Flight 1)
Camera auto-cycled on the ground post-landing and overwrote flight photos.

### Root cause
`telem_deps/util/photo_cleanup.py` deleted the **oldest** JPEGs first when
total photo storage exceeded 3 GB. Because the flight photos were the
oldest files on the SD card by the time landing happened, the on-ground
capture cycle (one photo every 10 s, forever) deleted them to make room
for new ground photos.

### Fix
- `photo_cleanup.py` now **never deletes**. It just measures total photo
  storage and returns a warning if the total exceeds a 30 GB soft cap.
  Since the SD card is 64 GB, 30 GB is a generous budget that won't fill
  up on a short flight.
- `camera_worker.py` was updated to emit a `CAMERA_STORAGE_WARN` event if
  that soft cap is ever crossed.
- No changes to the capture cadence (still 10 s).

## 2. Downlink image quality improvement

### Previously
Downlink thumbnails were 640×480 at JPEG quality 75 (~40–80 KB). Usable
but low fidelity, and the code wastefully invoked `rpicam-still` twice per
cycle (once at full, once at 800×600 thumb, then PIL downscaled to 640×480).

### Now
Downlink thumbnails are **1024×768 at JPEG quality 85** (~150–250 KB).
The thumbnail is generated by downscaling the captured full-res image in
PIL — no second `rpicam-still` invocation. This is faster, uses less
power, and guarantees the thumb matches the full image pixel-for-pixel
(no scene change between the two captures).

Expected downlink time per image, at 200 B DAP chunks + 50 ms inter-packet
delay: **~5–10 minutes**.

### FULL downlink removed
The old `unified_radio.py` had a branch that would downlink the full-res
4656×3496 image if the ground station requested `FULL`. At the current
radio parameters that takes ~2 hours of airtime per image, which is not
useful. The FULL branch now logs a message and falls back to the thumb.
If a GS operator still types `FULL` in their command args, they'll get a
thumb and a console note explaining why.

## 3. Systemd services — SSH lockout fix

### Symptom (Flight 1)
SSH'ing into the Pi was unreliable or impossible while the FSW was
running.

### Root cause (most likely)
The Flight 1 units attached to a TTY or otherwise consumed the console
input, and/or the watchdog reboot-stormed before sshd could stabilize.
The repo as uploaded did not contain the actual `.service` files, so I
rebuilt them from scratch with SSH-safe defaults.

### What's in `systemd/`
| Unit | Purpose | Runs as |
|---|---|---|
| `echo-incr-boot.service` | Bumps `boot_count.txt` at boot (oneshot) | `f25-echo2` |
| `echo-telem.service` | Main FSW telemetry + camera loop | `f25-echo2` |
| `echo-radio.service` | Unified radio (beacon + CAP/ACK + DAP) | `f25-echo2` |
| `echo-watchdog.service` | Supervises the above, restarts/reboots on failure | `root` |
| `apogee-video.service` | One-shot 60 s video at apogee (triggered on demand) | `f25-echo2` |

All services have:
- `StandardInput=null`, `StandardOutput=journal`, `StandardError=journal`
  (no TTY contention — this is the key SSH fix)
- `Restart=on-failure` with a 5-second backoff (not a busy loop)
- `WatchdogSec=` where the daemon supports `daemon.notify("WATCHDOG=1")`
- No `After=`/`Before=` dependency on `ssh.service` anywhere. SSH starts
  independently.

Watchdog retains `ENABLE_REBOOT_ON_ESCALATION = True` (you asked for it
to stay on). If you start reboot-storming during debugging, flip it to
`False` in `watchdog/watchdog.py` and `systemctl restart echo-watchdog`.

### Deploy
```bash
# As f25-echo2 on the Pi, in ~/echo_fsw/:
git pull
sudo bash systemd/install.sh
sudo systemctl start echo-telem.service echo-radio.service echo-watchdog.service
journalctl -u echo-telem.service -f
```

### Groups
The `f25-echo2` user needs access to SPI/I2C/GPIO for the radio and
sensors. Run once on the Pi:
```bash
sudo usermod -aG gpio,spi,i2c,dialout,video f25-echo2
```
Log out + back in for group changes to take effect.

## 4. Other bug fixes (the "clean everything up" pass)

### `telem_deps/app.py` — magnetometer tuple bug
`read_magnetometer()` already returns a 3-tuple. The old except handler was:
```python
rm_x = rm_y = rm_z = (None, None, None)
```
which assigned the whole tuple `(None, None, None)` to **each** of
`rm_x`, `rm_y`, `rm_z` — so on a mag read failure, `rm_x` was a tuple,
not `None`, and `_fmt_float_or_blank(rm_x, 3)` would raise. Fixed to
`rm_x = rm_y = rm_z = None`.

### `telem_deps/sensors/camera_worker.py` — dict mutation during iteration
`_altitude_loop` iterated `self._videos_captured.items()` and
`_trigger_altitude_video` mutated that same dict mid-iteration. CPython
tolerates this on small dicts most of the time but it's technically UB
and has caused `RuntimeError: dictionary changed size during iteration`
on at least one Pi in the wild. Fixed to iterate over
`list(self._videos_captured.items())`.

### `telem_deps/sensors/camera_worker.py` — sleep no longer blocks shutdown
The worker used `time.sleep(self.period)`, so `stop()` could take up to
10 seconds to return. Changed to `self._stop.wait(self.period)` so
shutdown is prompt.

### `telem_deps/incr_boot.sh` — smart-quotes bug
The initial-value line was:
```bash
echo "0" > "$FILE"
```
(with Unicode curly quotes, not ASCII). That writes the three bytes
`\xe2\x80\x9c 0 \xe2\x80\x9d` to `boot_count.txt`. Reading that with
`cat` and passing to `$(( ... + 1 ))` fails, and the counter stops
incrementing. Fixed with straight ASCII quotes, added validation, and
`set -euo pipefail` to fail fast if something's wrong.

### All hardcoded paths
Every `/home/f25-echo/echo_fsw/...` path was updated to
`/home/f25-echo2/echo_fsw/...` to match the new username. Places changed:
- `telem_deps/app.py` (GPS_OUTPUT_CSV, MAG_OUTPUT_CSV)
- `telem_deps/sensors/camera_worker.py` (BASE_DIR, VIDEO_DIR)
- `telem_deps/util/photo_cleanup.py` (PHOTO_BASE)
- `telem_deps/util/eventlog.py` (EVENT_LOG_PATH)
- `telem_deps/incr_boot.sh` (FILE)
- `radio/unified_radio.py` (THUMB_DIR, FULL_DIR)

## 6. Known gotchas for the next flight

1. **`apogee-video.service` races with the photo cycle.** The telem app
   triggers it via `systemctl start apogee-video.service` at apogee, but
   `camera_worker` keeps running in `echo-telem.service`, so you can have
   `rpicam-still` and `rpicam-vid` contending for the camera. Only one
   will win on any given frame; the other logs EBUSY. If this matters for
   your mission data, consider having `app.py` set a threading event that
   pauses the photo loop for the duration of the apogee video.

2. **`watchdog.py` imports `from systemd import daemon`.** The
   `systemd-python` package needs to be installed:
   ```bash
   sudo apt install python3-systemd
   ```
   If it's missing, the watchdog service will crash on start and
   `journalctl -u echo-watchdog.service` will show an ImportError.

3. **The RTC sync in `app.py` runs `sudo hwclock ...`** without a password
   prompt. For this to work non-interactively, the sudoers rules from
   `systemd/echo-fsw.sudoers` (or the equivalents) must be installed at
   `/etc/sudoers.d/echo-fsw`. Check the file for the exact entries.

4. **The watchdog can reboot you mid-debug.** If `echo-telem` or
   `echo-radio` fails to start 5 times in 5 minutes, the Pi reboots.
   During development, either set `ENABLE_REBOOT_ON_ESCALATION = False`
   in `watchdog/watchdog.py` or `sudo systemctl stop echo-watchdog`
   while you're working.
